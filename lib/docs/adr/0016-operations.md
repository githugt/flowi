# 0016: Operations extras are off by default, hand-rolled where a dependency would be larger than the feature

- **Status:** Accepted
- **Date:** 2026-10-10

## Context

Roadmap M8 adds nine small, independent items: OpenTelemetry traces, opt-in telemetry,
signed announcements, a changelog, blueprints, more digest sinks, a shared store for several
`flowi serve` instances, HTTP/3 and more colour themes. Most of them talk to the network or
to a user's infrastructure, and Flow-I is a tool people run against their own APIs: it must
never surprise them.

## Decision

- **Nothing happens until it is configured.** There is no built-in telemetry endpoint,
  announcements feed, collector or Valkey address. Each feature needs a setting (or an
  environment variable) naming where to talk, and the personal ones (`otel.*`, `telemetry*`,
  `announcements*`) can only be set at user level, so a cloned repository cannot choose where
  your data goes.
- **Telemetry is a closed catalogue.** `telemetry.Catalogue` lists every event and every
  allowed value (words or ranges). `Record` and `Send` refuse anything else, so a URL, name,
  id or path cannot be sent even by a bug. No install id; dates, not times. The preview
  (`flowi telemetry show`, the GUI dialog) is generated from the same catalogue, as is
  `docs/reference/telemetry.md`.
- **OTLP and Valkey are small clients on the standard library.** OTLP/HTTP with a JSON body
  (part of the OTLP spec) is one POST per finished run; the RESP2 client needs three commands.
  The OpenTelemetry SDK and a Redis client would each add more modules than the feature has
  lines. The only new dependency is `quic-go`, for HTTP/3, which cannot reasonably be written
  here. Trace and span ids derive from the run id and node path, so the engine can send a
  `traceparent` before the span exists and the exporter needs no shared state.
- **Exporting never affects a run.** The engine calls `Deps.Observe` for every event; the
  exporter queues finished traces and drops them when the queue is full. Telemetry and
  announcements failures are debug logs. The Valkey client is lazy, answers `ErrUnavailable`
  at once for 15 s after a failure, and a failed schedule-tick claim still runs the tick
  (a duplicate is better than a missed job).
- **Announcements are signed and distrusted anyway.** Ed25519 over the decoded payload,
  several trusted keys for rotation, https only, no redirects, 256 KiB, 3 s, a cache that is
  re-verified on every read, rollback refused, items stripped of control and invisible
  characters, https links only. The CLI fetches only on `flowi news`; the GUI loads them
  in the background on the Welcome tab.
- **Blueprints are flow bodies with parameters.** A reference may be `{param: name}`;
  string, int and bool parameters become inputs of the new flow with the given value as
  default, so templates keep working. Using a blueprint creates an ordinary flow with no link
  back. A blueprint made from a flow parameterises its same-collection references and inputs;
  with defaults it rebuilds the flow.
- **One changelog.** `CHANGELOG.md` in each app repo, generated by git-cliff from
  Conventional Commits, embedded in the binary and parsed by `flowi-lib/changelog` for
  `flowi changelog` and the GUI's "What's new".

## Consequences

- A build that ships a default telemetry endpoint, announcements URL/keys or OTLP collector
  must set them deliberately (two setting defaults each).
- Blueprint node bodies are checked after use, not inside the blueprint; the blueprint's JSON
  schema checks only node `id` and `type`.
- With Valkey down every instance fires every schedule tick.
- HTTP/3 refuses a configured proxy and does not fall back to TCP.
- The GUI has no release pipeline yet (cgo packaging); `.goreleaser.yaml` covers the CLI.
